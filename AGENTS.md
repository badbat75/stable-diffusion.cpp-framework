# Project guide

## Project overview

Windows-only PowerShell scripts to install prerequisites, configure, build, and run [stable-diffusion.cpp](https://github.com/leejet/stable-diffusion.cpp) with CUDA, Vulkan, and ROCm (HIP) support, and NSIS installer packaging. Not compatible with Linux or macOS. sd-server's built-in web UI is used as the frontend — no separate web UI is bundled. Architecture mirrors the sibling `llama.cpp-framework` repo one-to-one (same script names, same INI layout, same install-time flow).

## Structure

- `build\config-build.psd1` — build-time configuration (paths, GPU backend toggles). Generated by `01-configure.ps1`; lives under `build\` (whole dir gitignored). Runtime / per-model settings are **not** stored at repo root — they live under `%LOCALAPPDATA%\stable-diffusion.cpp\config\` and are written by `resources\config-server.ps1` / `config-model.ps1` on first launch (or by the NSIS install-time page).
- `common.ps1` — shared bootstrap: loads `$cfg` from `build\config-build.psd1`, adds ROCm/HIP\bin to PATH, exposes `Enable-VsDevShell` as a function. VS Dev Shell activation is **opt-in**: only build/package scripts call it.
- `00-install-prerequisites.ps1` — idempotent toolchain bootstrapper: installs **and** updates the winget-tracked packages (PowerShell 7+ / NSIS) in a single UAC-elevated session (`winget install` for missing, `winget upgrade` for present), then `git pull --ff-only`s `$cfg.StableDiffusionCppDir` when cloned (recursive, so the ggml submodule stays in sync). Flags CUDA / Vulkan / AMD HIP for manual install. Reads `build\config-build.psd1` directly (does **not** dot-source `common.ps1`) so it works on a fresh machine before `01-configure.ps1` has run. End-of-run report shows before→after versions, plus a rebuild recommendation (`02-build.ps1` / `03-package.ps1`) only when stable-diffusion.cpp source moved. Safe to re-run any time.
- `01-configure.ps1` — auto-detects paths, activates VS Dev Shell for tool discovery, verifies tools, creates `build\` if missing, writes `build\config-build.psd1`. Accepts `-StableDiffusionCppDir` param (defaults to `$PSScriptRoot\build\stable-diffusion.cpp`). Auto-probes for CUDA / Vulkan SDK / HIP and writes the matching GPU backend toggle (`SdCuda` / `SdVulkan` / `SdHipblas`) — at most one is `$true` at a time (priority: CUDA > Vulkan > HIP).
- `02-build.ps1` — dot-sources `common.ps1` + calls `Enable-VsDevShell`. Auto-clones/syncs sd.cpp recursively (`--recursive` for ggml submodule). CMake configure into `build\cmake-build` using `-DSD_BUILD_EXAMPLES=ON` and the active GPU toggle; builds with Ninja. Throws if more than one backend toggle is on.
- `03-package.ps1` — dot-sources `common.ps1` + calls `Enable-VsDevShell` (some installer steps need the VS env). Stages from `build\cmake-build\bin\` into `build\staging\bin\` plus runtime scripts and the icon, then builds NSIS installer to `.\dist\`.
- `resources\run-server.ps1` — runtime entry point shipped with the installer (main "stable-diffusion.cpp" Start Menu shortcut). Reads `%LOCALAPPDATA%\stable-diffusion.cpp\config\server.ini` for machine-wide knobs and `presets.ini` for per-model presets, picks one preset (auto if only one, interactive picker otherwise; accepts `-Preset <id>` to skip the picker), translates its keys into `sd-server` CLI args, and launches sd-server in the foreground. The user interacts with sd-server's built-in web UI at `http://<host>:<port>/`. Auto-invokes `config-server.ps1` / `config-model.ps1` if their outputs are missing. Accepts `-ServerExe` to override the binary location (e.g. point at an in-tree build at `.\build\cmake-build\bin\sd-server.exe`). Tees stdout+stderr to `%LOCALAPPDATA%\stable-diffusion.cpp\logs\sd-server.log`. CWD is forced to `%LOCALAPPDATA%\stable-diffusion.cpp` so first-run files don't land in Program Files.
- `resources\config-server.ps1` — sd-server config writer. Writes `%LOCALAPPDATA%\stable-diffusion.cpp\config\server.ini` (a single `[Server]` section). Holds machine-wide knobs only (Port, Hostname, Threads, ModelsDir); per-model params live in `presets.ini`. NSIS calls it with `-NonInteractive -Port -Hostname -Threads -ModelsDir` from the install-time page. Re-runnable via "Configure sd-server" Start Menu shortcut (the window auto-closes once the file is written — no `-NoExit`). Also supports `-DumpIni <path>`: emits the current `[Server]` values to a UTF-16 LE INI and exits without modifying anything; used by NSIS `.onInit` to surface previous values as install-page defaults. Also materializes `resources\mcp-config.template.json` → `%LOCALAPPDATA%\stable-diffusion.cpp\config\mcp.json` on every run, substituting `@SCRIPT_DIR@` with the directory containing `mcp-server.ps1` (uses `$PSScriptRoot`, which works in both dev mode and installed mode since `config-server.ps1` and `mcp-server.ps1` live side-by-side).
- `resources\config-model.ps1` — per-model preset builder. Operates directly on `%LOCALAPPDATA%\stable-diffusion.cpp\config\presets.ini` — the file `run-server.ps1` consumes at launch time. Lists `.gguf` / `.safetensors` files under `ModelsDir` (marks already-configured presets with `*`), prompts for sub-model paths (vae, llm, t5xxl, clip_l, clip_g, lora-model-dir, embd-dir), memory/perf knobs (type, offload-to-cpu, mmap, fa, diffusion-fa, clip-on-cpu, vae-on-cpu, max-vram), and default generation params (sampler, steps, cfg-scale, width, height), then **rewrites just the matching `[section]` while preserving every other section in the file byte-for-byte** (including comments and hand-added exotic keys). The section name is the id shown in `run-server.ps1`'s picker. Hand-edits within the section being re-wizarded are lost; hand-edits to *other* sections survive. Also refreshes `server.ini`'s `ModelsDir` pointer (in-place, comment-preserving). Re-runnable via "Configure model" Start Menu shortcut.
- `.mcp.json` (repo root) — project-scope MCP config that auto-registers `resources\mcp-server.ps1` for anyone who opens the repo in Claude Code. Uses a relative path so it works on any clone location. End-users who installed via the NSIS installer get an equivalent generated for them at `%LOCALAPPDATA%\stable-diffusion.cpp\config\mcp.json` (see `mcp-config.template.json` below) — they can pass it via `claude --mcp-config <path>` or merge its `mcpServers` entry into `~/.claude.json`. Both configs spawn the same script over stdio — Claude Code prompts to trust the project on first open.
- `resources\mcp-config.template.json` — agent-agnostic MCP client config template with a single `@SCRIPT_DIR@` placeholder for the directory holding `mcp-server.ps1`. Materialized by `config-server.ps1` into `%LOCALAPPDATA%\stable-diffusion.cpp\config\mcp.json` so any MCP-aware agent (Claude Code, etc.) can be pointed at it without hand-editing JSON. Uses forward slashes in the resolved path so the file stays valid JSON without backslash escaping and `pwsh.exe` accepts the path. The MCP server reads sd-server's host/port from `server.ini` at startup, so no host/port needs to be baked into this config.
- `resources\mcp-server.ps1` — Model Context Protocol server (stdio, JSON-RPC 2.0) that bridges Claude Code (or any MCP client) to a running sd-server. PowerShell-only — zero new install deps, since pwsh 7+ is already a project prerequisite. Reads sd-server's host/port from `server.ini`, exposes three tools: `generate_image` that POSTs to `/sdcpp/v1/img_gen` (native async endpoint) and polls `/sdcpp/v1/jobs/{id}` until done; `get_model_info` that GETs `/sdcpp/v1/capabilities` and returns a curated snapshot (model name/stem/path, current mode, supported features, defaults that will be applied to omitted fields, sampler/scheduler lists, dimension limits) — call it before `generate_image` to discover which knobs are meaningful for the active model. Supports MCP progress streaming: when the client includes `_meta.progressToken` in `tools/call`, the server emits `notifications/progress` on every state transition (`queued` → `generating` → `completed`) plus a 1-second heartbeat carrying elapsed seconds. sd-server has no step-level progress endpoint, so elapsed-time + status is the finest granularity available — there is no percentage to stream. Translates flat MCP arguments (`steps`, `cfg_scale`, `sampler`, `guidance`) into sd.cpp's nested `gen_params` schema (`sample_params.sample_steps`, `sample_params.guidance.txt_cfg`, etc.). Also supports img2img / reference inputs via `init_image`, `ref_images`, `strength`, and `auto_resize_ref_image` — each image arg accepts either a local file path (loaded and base64-encoded by `Resolve-ImageArgument`) or a pre-encoded base64 / `data:` URL, both forwarded to sd-server's top-level `init_image` / `ref_images` JSON fields. **Callers should pass file paths, not data URLs**: an LLM client cannot reliably emit a multi-KB base64 string verbatim in a tool call, so any image larger than a thumbnail will arrive truncated and sd-server will reject it with `invalid ref_images` / `load image from 'memory' failed`. Letting the MCP server read from disk sidesteps the model's verbatim-copy step entirely. `ref_images` only has effect on reference-aware models (Flux Kontext, OmniGen, etc.). Returns the image as MCP `image` content (base64, JPEG by default to keep model context cost low). Also supports an optional `save_path` arg that writes the rendered image(s) to disk (parent dir auto-created; batch_count > 1 gets `_001`, `_002`, ... suffixes before the extension). When `save_path` is set, inline image return is suppressed by default to avoid blowing up model context; pass `return_inline=true` to get both. When `save_path` is omitted the behaviour is unchanged — inline-only, matching the built-in web UI. The second tool, `encode_file_base64`, reads a local binary file and returns its base64 representation as a text block (optional `as_data_url` flag prepends `data:<mime>;base64,`); raw size is capped at 25 MB by default (`max_bytes` overrides). Intended for small files (few KB) or for surfacing base64 into the conversation when the caller genuinely needs it visible — **not for staging images into `generate_image`**, since the model truncates the multi-KB string when echoing it into the next tool call. To stage a reference image, pass the path directly to `generate_image`'s `ref_images` instead. Logging goes to stderr + `logs\mcp-server.log` — never stdout, which is reserved for the JSON-RPC stream. Requires sd-server already running (this script doesn't start it). To wire into Claude Code, add an entry to `~/.claude.json` or project `.mcp.json` pointing at `pwsh.exe -NoProfile -ExecutionPolicy Bypass -File <INSTDIR>\mcp-server.ps1`.
- `resources\common-functions.ps1` — shared helpers dot-sourced by all three runtime scripts (`config-server.ps1`, `config-model.ps1`, `run-server.ps1`). Currently exposes `Read-ServerIni` (parse the `[Server]` section into a hashtable of strings) and `Set-ServerIniField` (replace one key in `[Server]` while preserving comments, key order, and any other sections). Staged into `$INSTDIR` alongside the other runtime scripts and also extracted to `$PLUGINSDIR` in NSIS `.onInit` so the `-DumpIni` invocation there can dot-source it.
- `resources\stable-diffusion.ico` — installer / shortcut icon. Currently a placeholder (gradient square with "SD" text) generated by a `System.Drawing` one-liner; replace with a proper icon at any time.
- `stable-diffusion-cpp.nsi.template` — NSIS installer template with placeholders (`@VERSION@`, `@STAGING_DIR@`, `@OUTPUT_FILE@`) replaced by `03-package.ps1` into `build\stable-diffusion-cpp.nsi` (transient — deleted after the build). Has one custom nsDialogs page (server config: Port / CPU threads / Bind / Models folder browser) that drives `config-server.ps1 -NonInteractive` post-install to write `server.ini`. Thread defaults are pre-computed in `.onInit` from `%NUMBER_OF_PROCESSORS%` using the same formula as the runtime fallback. Models folder defaults to `$PROFILE\.stable-diffusion.cpp\models` (mirrored in `config-server.ps1`'s interactive fallback) and is created on disk if missing. When an existing `server.ini` is present, `.onInit` extracts `config-server.ps1` and `common-functions.ps1` to `$PLUGINSDIR` and runs the script with `-DumpIni` to override these defaults with the user's previous choices. Model-dependent params (paths, sampler, steps, cfg, dimensions, fa, offload, etc.) are NOT prompted at install — created lazily per-model by `config-model.ps1` on first run. Start Menu shortcuts target `pwsh.exe` (PowerShell 7+).

## Key conventions

- `common.ps1` is dot-sourced by build/package scripts only (not runtime scripts or `00-install-prerequisites.ps1` / `01-configure.ps1`). Runtime scripts use `$PSScriptRoot` to resolve their own paths.
- The Threads default in `config-server.ps1`, the runtime fallback in `resources\run-server.ps1`, and the NSIS `.onInit` formula use the **same expression**: `Threads = max(1, floor(cores * 0.5))`. Don't let them drift.
- `build\config-build.psd1` (build-time) uses single-quoted PowerShell-data-file syntax. All other generated config files (`server.ini`, `presets.ini`) are plain INI written as UTF-8 without BOM.
- All build artifacts live under `.\build\` (gitignored): source clone, cmake binary dir, NSIS staging, `config-build.psd1`, generated `.nsi`. A single `rm -rf build\` or `Remove-Item -Recurse -Force build\` returns the repo to a clean state.
- The installer registers in `HKLM\Software\stable-diffusion.cpp` (InstallDir) and supports upgrades (uninstalls previous version first). User runtime state lives under `%LOCALAPPDATA%\stable-diffusion.cpp\`: `config\server.ini` (machine-wide sd-server + ModelsDir — single `[Server]` section), `config\presets.ini` (per-model presets — one `[section]` per model file; hand-edits are preserved across `config-model.ps1` runs for any section the wizard does not touch), `logs\sd-server.log` (sd-server stdout/stderr), `logs\mcp-server.log` (MCP bridge log, only when used). sd-server itself does not persist generated images to disk; the MCP bridge persists only when the caller explicitly passes a `save_path` to `generate_image`, otherwise it also returns base64 only (matching the built-in web UI). The uninstaller asks (defaulting to No) whether to delete the whole tree, so it survives reinstall/upgrade by default.
- sd.cpp requires `--recursive` git clone because it depends on the ggml submodule. Build output is `build\cmake-build\bin\sd-server.exe` (Windows CMake puts binaries directly in `bin\`); Release / Debug fallback locations are checked when staging.
- Only one GPU backend may be enabled per build (CUDA, Vulkan, or HIP). `01-configure.ps1` auto-probes and picks one with priority CUDA > Vulkan > HIP; `02-build.ps1` enforces this.
