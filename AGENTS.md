# Project guide

## Project overview

Windows-only PowerShell scripts to install prerequisites, configure, build, and run [stable-diffusion.cpp](https://github.com/leejet/stable-diffusion.cpp) with CUDA, Vulkan, and ROCm (HIP) support, and NSIS installer packaging. Not compatible with Linux or macOS. sd-server's built-in web UI is used as the frontend — no separate web UI is bundled. Architecture mirrors the sibling `llama.cpp-framework` repo one-to-one (same script names, same INI layout, same install-time flow).

## Structure

- `build\config-build.psd1` — build-time configuration (paths, GPU backend toggles). Generated by `01-configure.ps1`; lives under `build\` (whole dir gitignored). Runtime / per-model settings are **not** stored at repo root — they live under `%LOCALAPPDATA%\stable-diffusion.cpp\config\` and are written exclusively by the `sd-config` GUI / CLI (the old `config-server.ps1` / `config-model.ps1` PowerShell wizards have been removed).
- `common.ps1` — shared bootstrap: loads `$cfg` from `build\config-build.psd1`, adds ROCm/HIP\bin to PATH, exposes `Enable-VsDevShell` as a function. VS Dev Shell activation is **opt-in**: only build/package scripts call it.
- `00-install-prerequisites.ps1` — idempotent toolchain bootstrapper: installs **and** updates the winget-tracked packages (PowerShell 7+ / NSIS) in a single UAC-elevated session (`winget install` for missing, `winget upgrade` for present; the elevated child ends with an explicit `exit 0` because winget's NO_APPLICABLE_UPGRADE would otherwise paint a false error, and a declined UAC prompt degrades to a warning instead of killing the run), then updates `$cfg.StableDiffusionCppDir` when cloned via `fetch` + `checkout master` + `pull --ff-only` (recovers a detached-HEAD clone; recursive, so the ggml submodule stays in sync, with a loud warning if the submodule sync fails). Flags CUDA / Vulkan / AMD HIP for manual install. Reads `build\config-build.psd1` directly (does **not** dot-source `common.ps1`) so it works on a fresh machine before `01-configure.ps1` has run. End-of-run report shows before→after versions. When anything it touches actually moved (a winget package upgrade **or** an sd.cpp source pull) it clears the stale CMake build cache (`build\cmake-build` + `build\staging`) so the next `02-build-server.ps1` reconfigures from scratch — `config-build.psd1` is preserved so `01-configure.ps1` need not be re-run — and the report recommends `02-build-server.ps1` / `04-package.ps1`. (Rationale: `CMakeCache.txt` bakes in absolute MSVC compiler paths; a VS toolset upgrade renames the `Tools\MSVC\<ver>` dir and CMake then refuses to reconfigure against the missing `cl.exe`.) Safe to re-run any time. Dot-sources `sdcpp-patches\patch-lib.ps1` (function-only, no `$cfg` dependency — safe pre-`01-configure`) and, when the clone exists, calls `Reset-SdCppClone` before its `git pull` and `Invoke-SdCppPatches` after, so the clone is left in its patched/built state and the before→after rebuild detection still keys off the real upstream HEAD.
- `sdcpp-patches\` — version-controlled local modifications layered onto the (gitignored, auto-pulled) sd.cpp clone, **without** committing into the clone's git or forking upstream. `patch-lib.ps1` exposes `Reset-SdCppClone` (revert: `git reset --hard HEAD` in both the parent clone **and** the ggml submodule — HEAD does not move in either — plus deletes the copied-in headers by name; the delete loop walks **every** patch-set directory including `.disabled` ones, so files copied in before a set was parked don't linger and break a future pull) and `Invoke-SdCppPatches` (per patch set: optional `base-commit.txt` drift warning — compared against the ggml submodule's HEAD when the set carries only a `ggml.patch`, against the clone's HEAD otherwise — copy `src\*` into the clone's `src\`, `git apply wiring.patch` at the root, `git -C ggml apply ggml.patch` inside the submodule; a forward-apply failure that succeeds in reverse is treated as "already merged upstream" and silently skipped, anything else throws loud). Each subfolder is one patch set (`src\*` new header-only sources, `wiring.patch` unified diff against tracked sd.cpp files, `ggml.patch` unified diff against tracked ggml files, `base-commit.txt` the SHA it was generated against, `README.md` the plan/regen steps). Comment-only / empty `wiring.patch` or `ggml.patch` is skipped so the harness builds vanilla upstream until a real patch lands. A patch set can also be **parked** by dropping a `.disabled` marker file in its directory — `Get-SdCppPatchSets` skips any set containing one (neither reset nor applied); delete the marker to re-enable. Current sets: `hidream-i1\` (**DISABLED 2026-06-09** via `.disabled` marker — experimental HiDream-I1 MMDiT port, parked but kept under version control now that the build follows vanilla upstream, which natively supports Ideogram4. Its root causes were fixed/verified — FluxFlow output sign, Llama-3.1 tokenization, CLIP-L `text_projection`/248-pos pooled — and it required flash attention OFF. See its `README.md` and project memory `hidream-i1-*`); `ggml-math-library-win32\` (single-line revert of `if (DEFINED MATH_LIBRARY)` → `if (MATH_LIBRARY)` in `ggml/src/CMakeLists.txt` so Windows configure doesn't fail with `MATH_LIBRARY=NOTFOUND linked by target ggml-base`; harmless on Linux/macOS, auto-skips when sd.cpp eventually bumps its ggml gitlink past the upstream revert in ggml `74f21355` / `v0.10.1`).
- `01-configure.ps1` — auto-detects paths, activates VS Dev Shell for tool discovery, verifies tools, creates `build\` if missing, writes `build\config-build.psd1`. Accepts `-StableDiffusionCppDir` param (defaults to `$PSScriptRoot\build\stable-diffusion.cpp`). Auto-probes for CUDA / Vulkan SDK / HIP and writes the matching GPU backend toggle (`SdCuda` / `SdVulkan` / `SdHipblas`) — at most one is `$true` at a time (priority: CUDA > Vulkan > HIP).
- `02-build-server.ps1` — dot-sources `common.ps1` + `sdcpp-patches\patch-lib.ps1`, calls `Enable-VsDevShell`. Auto-clones/syncs sd.cpp recursively (`--recursive` for ggml submodule). Around the sync: `Reset-SdCppClone` strips `sdcpp-patches\` edits **before** `git pull --ff-only` (so the pull always sees a clean tree and never throws), then `Invoke-SdCppPatches` re-applies them **after** the pull/submodule sync. A `$sdcppPin` variable near the top can override the pull (empty = follow upstream HEAD, non-empty SHA = `fetch` + `checkout --detach` to that commit) — kept as a debug knob, currently empty since the ggml MATH_LIBRARY break is patched locally. Detects `sccache` on PATH (mirrors `llama.cpp-framework\02-build.ps1`): when present, sets `SCCACHE_DIR=build\.sccache`, `SCCACHE_CACHE_SIZE=10G`, `SCCACHE_IDLE_TIMEOUT=0`, `SCCACHE_MAX_FRAME_LENGTH=100MB`, passes `-DCMAKE_{C,CXX}_COMPILER_LAUNCHER=<sccache>` — **C/C++ only, not CUDA**: sccache 0.15.0 mishandles nvcc's multi-phase compilation under CUDA 13.x, killing every CUDA TU with `fatbinary fatal : Could not open input file '*.cubin'` — and runs `sccache --show-stats` / `--stop-server` after the build. Builds **vanilla upstream** (Ideogram4 et al. are native as of upstream `19bdfe2`, 2026-06-04); the old forced `-DSD_HIDREAM_I1_EXPERIMENTAL=ON` was dropped 2026-06-09 along with parking the `hidream-i1` patch set. Does **not** pin `-DCMAKE_CUDA_HOST_COMPILER`: CUDA 13.x nvcc aborts when the 8.3-short `-ccbin` CMake emits differs from the long-form `cl.exe` on PATH (`nvcc fatal : cl.exe in PATH ... is different than one specified with -ccbin`), so it relies on `Enable-VsDevShell` putting the right `cl.exe` first instead. CMake configure into `build\cmake-build` using `-DSD_BUILD_EXAMPLES=ON` and the active GPU toggle; builds with Ninja (`-j` from `$cfg.BuildJobs`, default `max(1, cores - 4)`). Wipes `build\cmake-build\bin\` before building so binaries upstream renamed/dropped don't linger and get packaged. Throws if more than one backend toggle is on.
- `03-build-gui.ps1` — builds the Rust/Slint `sd-config` configurator (under `sd-config\`) via `cargo build --release`. Output: `sd-config\target\release\sd-config.exe`. Idempotent; safe to re-run; `04-package.ps1` calls it unconditionally (cargo no-ops when up to date). Errors with a clear message if `cargo` is not on PATH (suggesting `winget install Rustlang.Rustup`).
- `04-package.ps1` — dot-sources `common.ps1` + calls `Enable-VsDevShell` (build/package-script convention). Installer version = upstream `git describe` **plus** this repo's short SHA (`<describe>+h.<sha>`), so two harness revisions over the same upstream commit produce distinguishable installers. Stages from `build\cmake-build\bin\` into `build\staging\bin\` plus runtime scripts and the icon, then builds NSIS installer to `.\dist\`. Always invokes `03-build-gui.ps1` before staging `sd-config.exe` alongside `sd-server.exe` (an existence check alone would ship a stale GUI binary).
- `05-update-installed-scripts.ps1` — dev convenience: hash-compares `resources\*` + `sd-config.exe` against the NSIS-installed copy (InstallDir from `HKLM\Software\stable-diffusion.cpp`, fallback `%ProgramFiles%\stable-diffusion.cpp`) and copies only what changed, so runtime-script / GUI iterations don't need an installer rebuild. Self-elevates via UAC; the elevated child transcripts to a temp file that the caller prints afterwards (its own console closes on exit). `sd-server.exe` and the ggml DLLs are never touched — rebuild + reinstall for those.
- `sd-config\` — Rust crate (Slint UI + clap CLI) producing a single dual-mode binary `sd-config.exe`. No args → Slint GUI (Server / Models / MCP tabs) writing `server.ini` / `presets.ini` and the per-client MCP-config files. With subcommands → headless CLI (`server show|set`, `preset list|show|delete`, `mcp status|install|uninstall`). Reads/writes the same INI files that `run-server.ps1` and `mcp-server.ps1` consume; the "Bind to" combo lists detected IPv4 interfaces so users can pin sd-server to a specific adapter. The Models tab's LoRA "Add…" picker warns (cancellable rfd dialog) when the chosen file's parent dir differs case-insensitively from the last existing entry's, since all of a preset's LoRAs must share one directory; the pre-rename `lora-model-dir` key is round-tripped untouched via `Preset::legacy_lora_dir` (read-and-preserve passthrough, no widget) so editing an old preset never strips its `--lora-model-dir`. See [`sd-config\README.md`](sd-config/README.md) for the user-facing overview and CLI reference, and [`sd-config\docs\`](sd-config/docs/) for the implementation deep-dives ([`architecture.md`](sd-config/docs/architecture.md) — module layout, INI write contract, paths resolution, bind-to combo wiring; [`icon-wiring.md`](sd-config/docs/icon-wiring.md) — why the icon is plumbed through both the EXE resource fork and a runtime winit call; [`mcp-clients.md`](sd-config/docs/mcp-clients.md) — per-client JSON shapes and the surgical-edit contract).
- `resources\run-server.ps1` — runtime entry point shipped with the installer (main "stable-diffusion.cpp" Start Menu shortcut). Reads `%LOCALAPPDATA%\stable-diffusion.cpp\config\server.ini` for machine-wide knobs and `presets.ini` for per-model presets, picks one preset (auto if only one, interactive picker otherwise; accepts `-Preset <id>` to skip the picker), translates its keys into `sd-server` CLI args, and launches sd-server in the foreground. Per-preset LoRAs: a `lora` INI key holds FULL file paths like the other model keys (`vae`/`llm`/`t5xxl`), optionally suffixed `:<multiplier>` (default 1.0), comma-separated (parsed by `ConvertTo-LoraEntries` in common-functions.ps1); since sd-server has no per-file LoRA flag — only `--lora-model-dir` plus per-request relative paths — run-server.ps1 derives the dir from the first entry's parent (there is deliberately no separate `lora-model-dir` INI key; all of a preset's LoRAs must share one directory — `Write-Warning` fires per offending entry when one's parent differs case-insensitively from the first's, since only files in the first dir resolve), and the actual per-request application is injected by `mcp-server.ps1` (the built-in web UI has its own LoRA selector). Legacy migration: the pre-rename `lora-model-dir` directory key is still honoured — when a preset yields no `lora` file paths but carries `lora-model-dir`, that value is passed through to `--lora-model-dir` (sd-config round-trips the key untouched via `Preset::legacy_lora_dir`, never exposing it in the GUI), so old presets don't silently lose their LoRA dir. A `lora-apply-mode` key passes through to `--lora-apply-mode` (`auto` picks `at_runtime` on quantized weights — correct but adds per-step LoRA matmuls, measured ~9x slower per step on ideogram4 Q4_0 (79 s/it vs 8.5); `immediately` merges once into the weights at request time — fast steps, but the requant back to the quantized type eats part of the LoRA delta: invisible on pure restyling, decisive when the LoRA must fight the model's own attractors, where only `at_runtime` preserves the effect). The user interacts with sd-server's built-in web UI at `http://<host>:<port>/`. When `server.ini` or `presets.ini` are missing the script launches `$INSTDIR\bin\sd-config.exe` (GUI) with `Start-Process -Wait` so the user can configure interactively, then re-checks. Accepts `-ServerExe` to override the binary location (e.g. point at an in-tree build at `.\build\cmake-build\bin\sd-server.exe`); when omitted, resolves the binary from `HKLM:\Software\stable-diffusion.cpp\InstallDir\bin\sd-server.exe` (registry key written by the NSIS installer), falling back to `%ProgramFiles%\stable-diffusion.cpp\bin\sd-server.exe` — so the script works both from the installed copy and from `<repo>\resources\` when spawned by `mcp-server.ps1`'s project-scope `.mcp.json`. Also accepts `-NonInteractive` to suppress the "Press any key to close" prompts in the error trap and failed-exit branch (used by `mcp-server.ps1`'s `switch_preset` when it spawns this script detached with a hidden window). Launches sd-server via `System.Diagnostics.Process` (not a pipeline) to capture its actual PID and forwards stdout/stderr to console + `%LOCALAPPDATA%\stable-diffusion.cpp\logs\sd-server.log` via an in-process `SdLogPipe` C# helper (compiled via `Add-Type`) that reads raw chunks from each stream on `Task.Run` threads. The line-oriented `OutputDataReceived` / `BeginOutputReadLine` API was avoided because sd.cpp's progress bar emits `\r...\r...\r...\n` (only one newline at completion), and .NET's line-buffered event handler would hide every interim progress update until the final `\n`. Maps `server.ini`'s `Hostname` to `sd-server --listen-ip`: `localhost` → `127.0.0.1`, everything else (the literal `0.0.0.0` or a specific interface IP picked in the sd-config "Bind to" combo) is passed through verbatim. Pins `$psi.WorkingDirectory = $dataDir` so sd-server inherits a known-good CWD — without this, sd-server picks up whatever .NET `Environment.CurrentDirectory` the parent had (PowerShell's `Set-Location` only updates the provider state, NOT the .NET CWD); when run-server.ps1 is itself spawned via `Start-Process -WindowStyle Hidden` (mcp-server.ps1's `switch_preset` path), the inherited CWD is `C:\Windows\System32` and sd-server's default `--lora-model-dir = "."` then recursively walks System32, hitting Access-Denied entries that bubble up as HTTP 500 from `/sdcpp/v1/capabilities` and `/sdcpp/v1/img_gen`. While running, writes `%LOCALAPPDATA%\stable-diffusion.cpp\run\sd-server.state` (JSON: `pid`, `host`, `port`, `preset`, `server_exe`, `started_at`) — consumed by `mcp-server.ps1` (and any other tool) for start/stop management. The file is removed in the script's `finally` block, and the script exits with sd-server's exit code. Refuses to launch if an existing state file points at a live process that really is sd-server (`Test-SdServerAlive` checks binary path/name, not just PID existence — Windows recycles PIDs); stale state files are silently cleaned up, and the guard is re-checked right before process start since the sd-config interaction / preset picker can hold the script open for minutes. CWD is forced to `%LOCALAPPDATA%\stable-diffusion.cpp` so first-run files don't land in Program Files.
- `.mcp.json` (repo root) — project-scope MCP config that auto-registers `resources\mcp-server.ps1` for anyone who opens the repo in Claude Code. Uses a relative path so it works on any clone location. Both dev and end-user paths run the same script over stdio — Claude Code prompts to trust the project on first open. End-users who want global registration use the sd-config GUI's MCP tab (or `sd-config mcp install <client>`) which writes into the client's own config file directly.
- `resources\mcp-server.ps1` — Model Context Protocol server (stdio, JSON-RPC 2.0) that bridges Claude Code (or any MCP client) to a running sd-server. PowerShell-only — zero new install deps, since pwsh 7+ is already a project prerequisite. The sd-server endpoint URL is resolved dynamically by `Get-SdServerBaseUrl` on every HTTP call: it prefers `run\sd-server.state` (authoritative — reflects what the live process actually bound to) and falls back to `server.ini` only when no live state file exists, so a `switch_preset` that changes host/port is observable mid-session without restarting mcp-server. Exposes nine tools:
  - `generate_image` — submit a render to sd-server's native async endpoint (POST `/sdcpp/v1/img_gen`) and return immediately. **Fire-and-forget by default** (`wait` omitted/false): it persists a small job-meta JSON at `run\jobs\<jobId>.json` — carrying `save_path` / `return_inline` / `started_at` / a replayable params `snapshot` across the async gap, since the later status call only receives a job id — and returns `{job_id, status:"submitted"}`; the caller then polls `check_image_job`. Pass `wait=true` to instead block until the render finishes, polling `/sdcpp/v1/jobs/{id}` internally (10 s per-poll timeout, up to 3 consecutive poll failures tolerated, job cancel attempted on give-up/timeout) and streaming `notifications/progress`, returning the image inline as before. Translates flat MCP arguments (`steps`, `cfg_scale`, `sampler`, `guidance`) into sd.cpp's nested `gen_params` schema (`sample_params.sample_steps`, `sample_params.guidance.txt_cfg`, etc.). Per-preset LoRAs auto-apply: sd-server's APIs intentionally refuse `<lora:...>` prompt tags (LoRAs ride a structured `lora` array of `{path, multiplier}` with paths relative to `--lora-model-dir`), so `Get-ActivePresetLoraList` reads the active preset's `lora` INI key and injects the array (bare filenames — run-server.ps1 derived the dir from the same key) into every img_gen request (logging a one-shot `WARN` when entries span more than one directory, since only the first dir's files resolve); an optional `lora_multiplier` request arg overrides the INI multiplier for that single call (applies to all entries, `0` disables them; the INI value, e.g. `:0.6`, stays the default); applied LoRAs are recorded in the `save_path` sidecar with their effective multiplier. Supports txt2img / img2img (`init_image` + `strength`) / reference-aware models (`ref_images`, only effective on Flux Kontext, OmniGen, etc.) — each image arg accepts either a local file path (loaded and base64-encoded by `Resolve-ImageArgument`) or a pre-encoded base64 / `data:` URL. **Callers should pass file paths, not data URLs**: an LLM client cannot reliably emit a multi-KB base64 string verbatim in a tool call, so anything larger than a thumbnail arrives truncated and sd-server rejects it with `invalid ref_images` / `load image from 'memory' failed`. Returns the image as MCP `image` content (base64, JPEG by default to keep model context cost low). Optional `save_path` writes the rendered image(s) to disk (parent dir auto-created; `batch_count > 1` gets `_001`, `_002`, ... suffixes) plus a `<stem>.json` sidecar with the flat request params so the call can be replayed; when `save_path` is set, inline return is suppressed by default (`return_inline=true` gets both). The prompt is either plain `prompt` (string) or `prompt_json` (a structured caption **object** for JSON-caption-native models — currently Ideogram4, whose Qwen3-VL conditioning degenerates to a grey "blocked" card on any plain-text prompt). The bridge serializes `prompt_json` compactly server-side (so the LLM client never hand-escapes a multi-KB JSON into a quoted string), and refuses plain-text prompts when the active model is JSON-native — unless the prompt already starts with `{` (pre-serialized caption) — detected by name-matching `ideogram` against the loaded model filename from `/sdcpp/v1/capabilities` (fallback: the preset id in `run\sd-server.state`), since neither the API nor the state file names the text encoder. Result delivery (disk save + `<stem>.json` sidecar + inline `image` content + summary) is factored into the shared `Complete-ImageJob`, used by both the `wait=true` path and `check_image_job`, so the async and blocking modes save/return byte-for-byte identically.
  - `check_image_job` (args: optional `job_id`) — consult an async job's progress and collect its result: GET `/sdcpp/v1/jobs/{id}` once (single poll, never blocks). While `queued`/`generating` it returns `{status, queue_position, elapsed_sec, done:false}` (`elapsed_sec` from the stashed `started_at`); on `completed` it reads the job-meta and hands the image(s) back through `Complete-ImageJob` — honouring the original `save_path`/`return_inline` and writing the params sidecar — then deletes the meta file; on `failed`/`cancelled` it returns `isError` with sd-server's reason and drops the meta; on an HTTP **404** (sd-server responded but has forgotten the job — e.g. it was restarted) it drops the meta and returns a clean non-error `status:"unknown"` result, so a zombie meta can't pollute the pending list forever (any OTHER poll failure — connection refused / timeout — is rethrown, NOT deleted, since the job may still exist). A 7-day GC at startup (right after `$script:JobsDir` is set) also prunes `run\jobs\*.json` older than 7 days by `LastWriteTime` (wrapped in try/catch) so never-polled jobs from crashed/abandoned clients don't accumulate. Called with **no** `job_id` it lists the locally-tracked pending jobs (the `run\jobs\*.json` files, with job_id + started_at + save_path + prompt preview). A missing meta file (job started by the web UI, or mcp-server restarted) degrades delivery to inline-only. Job ids are validated against `^[A-Za-z0-9_.-]+$` before use as a filename so they can't escape `run\jobs\`.
  - `cancel_image_job` (args: `job_id`) — POST `/sdcpp/v1/jobs/{id}/cancel` and delete the local meta; a job that already finished or never existed is reported back as a message, not raised as an error.
  - `get_model_info` — GET `/sdcpp/v1/capabilities` and return a curated snapshot (model name/stem/path, `prompt_format` = `plain-text` | `structured-json` with a schema note for the latter, current mode, supported features, defaults applied to omitted fields, sampler/scheduler lists, dimension limits). Call it before `generate_image` to discover which knobs are meaningful for the active model.
  - `encode_file_base64` — read a local binary file and return its base64 representation as a text block (optional `as_data_url` flag prepends `data:<mime>;base64,`); raw size capped at 25 MB by default (`max_bytes` overrides). Intended for small files or for surfacing base64 into the conversation — do NOT chain into `generate_image` (the model truncates the multi-KB string when echoing it into the next tool call; pass the path directly to `ref_images`/`init_image` instead).
  - `server_status` — read `run\sd-server.state` and probe `/sdcpp/v1/capabilities`; returns `running`/`ready` flags + pid/host/port/url/preset/started_at.
  - `list_presets` — parse `presets.ini` via `Get-Presets`, surface id + key params for each section, flag the active preset.
  - `switch_preset` (args: `preset`, optional `timeout_sec`=180) — `Stop-Process` current sd-server (if any), wait for `run-server.ps1`'s `finally` to clean the state file, then spawn `pwsh.exe -File run-server.ps1 -Preset <id> -NonInteractive` via `Start-Process -WindowStyle Hidden -PassThru` (single-string `-ArgumentList` so `$INSTDIR` paths containing spaces like `Program Files` survive intact) and poll `/sdcpp/v1/capabilities` until ready. No-op when the requested preset is already active. Streams `notifications/progress` (stop / start / "loading model... Ns elapsed") when the client passes a progressToken.
  - `stop_server` — `Stop-Process` the running sd-server by pid from the state file (after `Test-SdServerAlive` confirms the PID still belongs to sd-server — a recycled PID is treated as stale state, never killed). No-op when nothing is running. Note: this closes the user's foreground "stable-diffusion.cpp" console window if they launched it via the Start Menu shortcut.

  Progress: the default `generate_image` is fire-and-forget, so progress is **consulted on demand** by re-calling `check_image_job` (status / queue position / elapsed) rather than streamed — this is what stops a multi-minute render from tying up the tool call. The blocking paths (`generate_image wait=true`, `switch_preset`) still stream MCP progress: when the client includes `_meta.progressToken` in `tools/call`, the server emits `notifications/progress` on every state transition (`queued` → `generating` → `completed`) plus a 1-second heartbeat carrying elapsed seconds. sd-server has no step-level progress endpoint, so elapsed-time + status is the finest granularity available — there is no percentage to stream. HTTP error bodies from sd-server (e.g. `invalid ref_images`) are appended to the error surfaced to the client. Logging goes to stderr + `logs\mcp-server.log` — never stdout, which is reserved for the JSON-RPC stream (stdin/stdout are both forced to BOM-less UTF-8; stdin would otherwise decode as the OEM codepage and mangle non-ASCII prompts). `generate_image`, `check_image_job`, `cancel_image_job` and `get_model_info` need sd-server up; `switch_preset` starts it when nothing is running. To wire into Claude Code, add an entry to `~/.claude.json` or project `.mcp.json` pointing at `pwsh.exe -NoProfile -ExecutionPolicy Bypass -File <INSTDIR>\mcp-server.ps1`.
- `resources\common-functions.ps1` — shared helpers dot-sourced by `run-server.ps1` and `mcp-server.ps1`. After the sd-config GUI/CLI replaced the PowerShell wizards, the file shrank to read-side helpers only: `Read-ServerIni` (parse the `[Server]` section into a hashtable of strings), `Get-Presets` (parse `presets.ini` into an array of `{ Id, Keys }`), `Read-SdServerState` (read `run\sd-server.state` JSON), `Test-SdServerAlive` (state-file PID is alive **and** actually is sd-server — binary-path/name identity check against PID recycling, used by every liveness consumer), `ConvertTo-LoraEntries` (parse a preset's `lora` key — full path + optional `:<multiplier>` entries; the trailing segment is a multiplier only when numeric, so the drive colon never splits the path), and the `ConvertTo-IntOrNull / FloatOrNull / BoolOrNull` coercions. INI writes happen exclusively in Rust now (`sd-config\src\ini.rs`), which mirrors the same dialect byte-for-byte so the comment-preservation contract is preserved across both readers.
- `resources\stable-diffusion.ico` — installer / shortcut icon. Currently a placeholder (gradient square with "SD" text) generated by a `System.Drawing` one-liner; replace with a proper icon at any time.
- `stable-diffusion-cpp.nsi.template` — NSIS installer template with placeholders (`@VERSION@`, `@STAGING_DIR@`, `@OUTPUT_FILE@`) replaced by `04-package.ps1` into `build\stable-diffusion-cpp.nsi` (transient — deleted after the build). Pages: Welcome → Directory → Components → InstFiles → Finish. **No install-time configuration page**: server.ini / presets.ini / MCP-client configs are all written by the `sd-config` GUI post-install. The Finish page offers a `MUI_FINISHPAGE_RUN` checkbox (default unchecked so silent installs don't pop the GUI) whose handler `LaunchConfigurator` spawns `sd-config.exe` via `Exec '"$WINDIR\explorer.exe" "$INSTDIR\bin\sd-config.exe"'` — the explorer indirection is a standard NSIS trick to drop the installer's admin token so the launched process inherits the calling user's session (otherwise it would write to the admin's `%LOCALAPPDATA%` instead of the user's). `.onInit` flips `SetRegView 64`, sets `SetShellVarContext all` (per-machine install → all-users Start Menu; the few `$LOCALAPPDATA` uses temporarily switch back to `current` since NSIS maps it to ProgramData under `all`), and runs the previous-install check there — not in a custom page, which would be skipped under `/S` — with `/SD IDYES` so silent upgrades uninstall the old version too. The ARP entry carries `DisplayIcon` and `EstimatedSize`. The Start Menu carries three shortcuts: the launcher (`run-server.ps1` via `pwsh.exe`), "Configure" pointing at `$INSTDIR\bin\sd-config.exe` directly, and "Uninstall".

## Key conventions

- `common.ps1` is dot-sourced by build/package scripts only (not runtime scripts or `00-install-prerequisites.ps1` / `01-configure.ps1`). Runtime scripts use `$PSScriptRoot` to resolve their own paths.
- The Threads default in `sd-config\src\server_cfg.rs` (`default_threads`) and the runtime fallback in `resources\run-server.ps1` use the **same expression**: `Threads = max(1, floor(logical cores * 0.5))`. Don't let them drift. Note run-server.ps1 always passes `-t` (computing this fallback itself when `Threads` is blank) — sd-server never picks its own default.
- `build\config-build.psd1` (build-time) uses single-quoted PowerShell-data-file syntax. All other generated config files (`server.ini`, `presets.ini`) are plain INI written as UTF-8 without BOM.
- All build artifacts live under `.\build\` (gitignored): source clone, cmake binary dir, NSIS staging, `config-build.psd1`, generated `.nsi`, sccache cache (`build\.sccache\`). A single `rm -rf build\` or `Remove-Item -Recurse -Force build\` returns the repo to a clean state — that nukes the sccache too, so the next full build re-fills it from scratch.
- The installer registers in `HKLM\Software\stable-diffusion.cpp` (InstallDir) and supports upgrades (uninstalls previous version first). User runtime state lives under `%LOCALAPPDATA%\stable-diffusion.cpp\`: `config\server.ini` (machine-wide sd-server + ModelsDir — single `[Server]` section), `config\presets.ini` (per-model presets — one `[section]` per model file; hand-edits to non-touched sections are preserved across sd-config rewrites), `logs\sd-server.log` (sd-server stdout/stderr), `logs\mcp-server.log` (MCP bridge log, only when used), `run\sd-server.state` (JSON written by `run-server.ps1` while sd-server is running — pid/host/port/preset, used by `mcp-server.ps1` to detect/manage the live process; removed on graceful shutdown), `run\jobs\<jobId>.json` (per-job metadata stashed by `mcp-server.ps1`'s fire-and-forget `generate_image` — save_path/return_inline/started_at/params snapshot — read + deleted by `check_image_job`/`cancel_image_job` when the job reaches a terminal state). sd-server itself does not persist generated images to disk; the MCP bridge persists only when the caller explicitly passes a `save_path` to `generate_image`, otherwise it also returns base64 only (matching the built-in web UI). The uninstaller asks (defaulting to No) whether to delete the whole tree, so it survives reinstall/upgrade by default.
- sd.cpp requires `--recursive` git clone because it depends on the ggml submodule. Build output is `build\cmake-build\bin\sd-server.exe` (Windows CMake puts binaries directly in `bin\`); Release / Debug fallback locations are checked when staging.
- Only one GPU backend may be enabled per build (CUDA, Vulkan, or HIP). `01-configure.ps1` auto-probes and picks one with priority CUDA > Vulkan > HIP; `02-build-server.ps1` enforces this.
