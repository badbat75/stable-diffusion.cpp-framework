# Project guide

## Project overview

Windows-only PowerShell scripts to install prerequisites, configure, build, and run [stable-diffusion.cpp](https://github.com/leejet/stable-diffusion.cpp) with CUDA, Vulkan, and ROCm (HIP) support, and NSIS installer packaging. Not compatible with Linux or macOS. sd-server's built-in web UI is used as the frontend — no separate web UI is bundled. Architecture mirrors the sibling `llama.cpp-framework` repo one-to-one (same script names, same INI layout, same install-time flow).

## Structure

- `build\config-build.psd1` — build-time configuration (paths, GPU backend toggles). Generated by `01-configure.ps1`; lives under `build\` (whole dir gitignored). Runtime / per-model settings are **not** stored at repo root — they live under `%LOCALAPPDATA%\stable-diffusion.cpp\config\` and are written exclusively by the `sd-config` GUI / CLI (the old `config-server.ps1` / `config-model.ps1` PowerShell wizards have been removed).
- `common.ps1` — shared bootstrap: loads `$cfg` from `build\config-build.psd1`, adds ROCm/HIP\bin to PATH, exposes `Enable-VsDevShell` as a function. VS Dev Shell activation is **opt-in**: only build/package scripts call it.
- `00-install-prerequisites.ps1` — idempotent toolchain bootstrapper: installs **and** updates the winget-tracked packages (PowerShell 7+ / NSIS) in a single UAC-elevated session (`winget install` for missing, `winget upgrade` for present), then `git pull --ff-only`s `$cfg.StableDiffusionCppDir` when cloned (recursive, so the ggml submodule stays in sync). Flags CUDA / Vulkan / AMD HIP for manual install. Reads `build\config-build.psd1` directly (does **not** dot-source `common.ps1`) so it works on a fresh machine before `01-configure.ps1` has run. End-of-run report shows before→after versions. When anything it touches actually moved (a winget package upgrade **or** an sd.cpp source pull) it clears the stale CMake build cache (`build\cmake-build` + `build\staging`) so the next `02-build-server.ps1` reconfigures from scratch — `config-build.psd1` is preserved so `01-configure.ps1` need not be re-run — and the report recommends `02-build-server.ps1` / `04-package.ps1`. (Rationale: `CMakeCache.txt` bakes in absolute MSVC compiler paths; a VS toolset upgrade renames the `Tools\MSVC\<ver>` dir and CMake then refuses to reconfigure against the missing `cl.exe`.) Safe to re-run any time.
- `01-configure.ps1` — auto-detects paths, activates VS Dev Shell for tool discovery, verifies tools, creates `build\` if missing, writes `build\config-build.psd1`. Accepts `-StableDiffusionCppDir` param (defaults to `$PSScriptRoot\build\stable-diffusion.cpp`). Auto-probes for CUDA / Vulkan SDK / HIP and writes the matching GPU backend toggle (`SdCuda` / `SdVulkan` / `SdHipblas`) — at most one is `$true` at a time (priority: CUDA > Vulkan > HIP).
- `02-build-server.ps1` — dot-sources `common.ps1` + calls `Enable-VsDevShell`. Auto-clones/syncs sd.cpp recursively (`--recursive` for ggml submodule). CMake configure into `build\cmake-build` using `-DSD_BUILD_EXAMPLES=ON` and the active GPU toggle; builds with Ninja. Throws if more than one backend toggle is on.
- `03-build-gui.ps1` — builds the Rust/Slint `sd-config` configurator (under `sd-config\`) via `cargo build --release`. Output: `sd-config\target\release\sd-config.exe`. Idempotent; safe to re-run; `04-package.ps1` calls it lazily. Errors with a clear message if `cargo` is not on PATH (suggesting `winget install Rustlang.Rustup`).
- `04-package.ps1` — dot-sources `common.ps1` + calls `Enable-VsDevShell` (some installer steps need the VS env). Stages from `build\cmake-build\bin\` into `build\staging\bin\` plus runtime scripts and the icon, then builds NSIS installer to `.\dist\`. Auto-invokes `03-build-gui.ps1` if `sd-config\target\release\sd-config.exe` is missing and stages it alongside `sd-server.exe`.
- `sd-config\` — Rust crate (Slint UI + clap CLI) producing a single dual-mode binary `sd-config.exe`. No args → Slint GUI (Server / Models / MCP tabs) writing `server.ini` / `presets.ini` and the per-client MCP-config files. With subcommands → headless CLI (`server show|set`, `preset list|show|delete`, `mcp status|install|uninstall`). Reads/writes the same INI files that `run-server.ps1` and `mcp-server.ps1` consume; the "Bind to" combo lists detected IPv4 interfaces so users can pin sd-server to a specific adapter. See [`sd-config\README.md`](sd-config/README.md) for the user-facing overview and CLI reference, and [`sd-config\docs\`](sd-config/docs/) for the implementation deep-dives ([`architecture.md`](sd-config/docs/architecture.md) — module layout, INI write contract, paths resolution, bind-to combo wiring; [`icon-wiring.md`](sd-config/docs/icon-wiring.md) — why the icon is plumbed through both the EXE resource fork and a runtime winit call; [`mcp-clients.md`](sd-config/docs/mcp-clients.md) — per-client JSON shapes and the surgical-edit contract).
- `resources\run-server.ps1` — runtime entry point shipped with the installer (main "stable-diffusion.cpp" Start Menu shortcut). Reads `%LOCALAPPDATA%\stable-diffusion.cpp\config\server.ini` for machine-wide knobs and `presets.ini` for per-model presets, picks one preset (auto if only one, interactive picker otherwise; accepts `-Preset <id>` to skip the picker), translates its keys into `sd-server` CLI args, and launches sd-server in the foreground. The user interacts with sd-server's built-in web UI at `http://<host>:<port>/`. When `server.ini` or `presets.ini` are missing the script launches `$INSTDIR\bin\sd-config.exe` (GUI) with `Start-Process -Wait` so the user can configure interactively, then re-checks. Accepts `-ServerExe` to override the binary location (e.g. point at an in-tree build at `.\build\cmake-build\bin\sd-server.exe`); when omitted, resolves the binary from `HKLM:\Software\stable-diffusion.cpp\InstallDir\bin\sd-server.exe` (registry key written by the NSIS installer), falling back to `%ProgramFiles%\stable-diffusion.cpp\bin\sd-server.exe` — so the script works both from the installed copy and from `<repo>\resources\` when spawned by `mcp-server.ps1`'s project-scope `.mcp.json`. Also accepts `-NonInteractive` to suppress the "Press any key to close" prompts in the error trap and failed-exit branch (used by `mcp-server.ps1`'s `switch_preset` when it spawns this script detached with a hidden window). Launches sd-server via `System.Diagnostics.Process` (not a pipeline) to capture its actual PID and forwards stdout/stderr to console + `%LOCALAPPDATA%\stable-diffusion.cpp\logs\sd-server.log` via an in-process `SdLogPipe` C# helper (compiled via `Add-Type`) that reads raw chunks from each stream on `Task.Run` threads. The line-oriented `OutputDataReceived` / `BeginOutputReadLine` API was avoided because sd.cpp's progress bar emits `\r...\r...\r...\n` (only one newline at completion), and .NET's line-buffered event handler would hide every interim progress update until the final `\n`. Maps `server.ini`'s `Hostname` to `sd-server --listen-ip`: `localhost` → `127.0.0.1`, everything else (the literal `0.0.0.0` or a specific interface IP picked in the sd-config "Bind to" combo) is passed through verbatim. Pins `$psi.WorkingDirectory = $dataDir` so sd-server inherits a known-good CWD — without this, sd-server picks up whatever .NET `Environment.CurrentDirectory` the parent had (PowerShell's `Set-Location` only updates the provider state, NOT the .NET CWD); when run-server.ps1 is itself spawned via `Start-Process -WindowStyle Hidden` (mcp-server.ps1's `switch_preset` path), the inherited CWD is `C:\Windows\System32` and sd-server's default `--lora-model-dir = "."` then recursively walks System32, hitting Access-Denied entries that bubble up as HTTP 500 from `/sdcpp/v1/capabilities` and `/sdcpp/v1/img_gen`. While running, writes `%LOCALAPPDATA%\stable-diffusion.cpp\run\sd-server.state` (JSON: `pid`, `host`, `port`, `preset`, `server_exe`, `started_at`) — consumed by `mcp-server.ps1` (and any other tool) for start/stop management. The file is removed in the script's `finally` block. Refuses to launch if an existing state file points at a still-alive PID; stale state files (PID gone) are silently cleaned up. CWD is forced to `%LOCALAPPDATA%\stable-diffusion.cpp` so first-run files don't land in Program Files.
- `.mcp.json` (repo root) — project-scope MCP config that auto-registers `resources\mcp-server.ps1` for anyone who opens the repo in Claude Code. Uses a relative path so it works on any clone location. Both dev and end-user paths run the same script over stdio — Claude Code prompts to trust the project on first open. End-users who want global registration use the sd-config GUI's MCP tab (or `sd-config mcp install <client>`) which writes into the client's own config file directly.
- `resources\mcp-server.ps1` — Model Context Protocol server (stdio, JSON-RPC 2.0) that bridges Claude Code (or any MCP client) to a running sd-server. PowerShell-only — zero new install deps, since pwsh 7+ is already a project prerequisite. The sd-server endpoint URL is resolved dynamically by `Get-SdServerBaseUrl` on every HTTP call: it prefers `run\sd-server.state` (authoritative — reflects what the live process actually bound to) and falls back to `server.ini` only when no live state file exists, so a `switch_preset` that changes host/port is observable mid-session without restarting mcp-server. Exposes seven tools:
  - `generate_image` — POST `/sdcpp/v1/img_gen` (native async endpoint) and poll `/sdcpp/v1/jobs/{id}` until done. Supports txt2img / img2img (`init_image` + `strength`) / reference-aware models (`ref_images`). Optional `save_path` to dump to disk; otherwise returns base64 inline.
  - `get_model_info` — GET `/sdcpp/v1/capabilities` and return a curated snapshot (model name/stem/path, current mode, supported features, defaults applied to omitted fields, sampler/scheduler lists, dimension limits). Call it before `generate_image` to discover which knobs are meaningful for the active model.
  - `encode_file_base64` — read a local binary file, return base64 (debug aid; do NOT chain into `generate_image` — pass paths directly).
  - `server_status` — read `run\sd-server.state` and probe `/sdcpp/v1/capabilities`; returns `running`/`ready` flags + pid/host/port/url/preset/started_at.
  - `list_presets` — parse `presets.ini` via `Get-Presets`, surface id + key params for each section, flag the active preset.
  - `switch_preset` (args: `preset`, optional `timeout_sec`=180) — `Stop-Process` current sd-server (if any), wait for `run-server.ps1`'s `finally` to clean the state file, then spawn `pwsh.exe -File run-server.ps1 -Preset <id> -NonInteractive` via `Start-Process -WindowStyle Hidden -PassThru` (single-string `-ArgumentList` so `$INSTDIR` paths containing spaces like `Program Files` survive intact) and poll `/sdcpp/v1/capabilities` until ready. No-op when the requested preset is already active. Streams `notifications/progress` (stop / start / "loading model... Ns elapsed") when the client passes a progressToken.
  - `stop_server` — `Stop-Process` the running sd-server by pid from the state file. No-op when nothing is running. Note: this closes the user's foreground "stable-diffusion.cpp" console window if they launched it via the Start Menu shortcut. Supports MCP progress streaming: when the client includes `_meta.progressToken` in `tools/call`, the server emits `notifications/progress` on every state transition (`queued` → `generating` → `completed`) plus a 1-second heartbeat carrying elapsed seconds. sd-server has no step-level progress endpoint, so elapsed-time + status is the finest granularity available — there is no percentage to stream. Translates flat MCP arguments (`steps`, `cfg_scale`, `sampler`, `guidance`) into sd.cpp's nested `gen_params` schema (`sample_params.sample_steps`, `sample_params.guidance.txt_cfg`, etc.). Also supports img2img / reference inputs via `init_image`, `ref_images`, `strength`, and `auto_resize_ref_image` — each image arg accepts either a local file path (loaded and base64-encoded by `Resolve-ImageArgument`) or a pre-encoded base64 / `data:` URL, both forwarded to sd-server's top-level `init_image` / `ref_images` JSON fields. **Callers should pass file paths, not data URLs**: an LLM client cannot reliably emit a multi-KB base64 string verbatim in a tool call, so any image larger than a thumbnail will arrive truncated and sd-server will reject it with `invalid ref_images` / `load image from 'memory' failed`. Letting the MCP server read from disk sidesteps the model's verbatim-copy step entirely. `ref_images` only has effect on reference-aware models (Flux Kontext, OmniGen, etc.). Returns the image as MCP `image` content (base64, JPEG by default to keep model context cost low). Also supports an optional `save_path` arg that writes the rendered image(s) to disk (parent dir auto-created; batch_count > 1 gets `_001`, `_002`, ... suffixes before the extension). When `save_path` is set, inline image return is suppressed by default to avoid blowing up model context; pass `return_inline=true` to get both. When `save_path` is omitted the behaviour is unchanged — inline-only, matching the built-in web UI. The second tool, `encode_file_base64`, reads a local binary file and returns its base64 representation as a text block (optional `as_data_url` flag prepends `data:<mime>;base64,`); raw size is capped at 25 MB by default (`max_bytes` overrides). Intended for small files (few KB) or for surfacing base64 into the conversation when the caller genuinely needs it visible — **not for staging images into `generate_image`**, since the model truncates the multi-KB string when echoing it into the next tool call. To stage a reference image, pass the path directly to `generate_image`'s `ref_images` instead. Logging goes to stderr + `logs\mcp-server.log` — never stdout, which is reserved for the JSON-RPC stream. Requires sd-server already running (this script doesn't start it). To wire into Claude Code, add an entry to `~/.claude.json` or project `.mcp.json` pointing at `pwsh.exe -NoProfile -ExecutionPolicy Bypass -File <INSTDIR>\mcp-server.ps1`.
- `resources\common-functions.ps1` — shared helpers dot-sourced by `run-server.ps1` and `mcp-server.ps1`. After the sd-config GUI/CLI replaced the PowerShell wizards, the file shrank to read-side helpers only: `Read-ServerIni` (parse the `[Server]` section into a hashtable of strings), `Get-Presets` (parse `presets.ini` into an array of `{ Id, Keys }`), `Read-SdServerState` (read `run\sd-server.state` JSON), and the `ConvertTo-IntOrNull / FloatOrNull / BoolOrNull` coercions. INI writes happen exclusively in Rust now (`sd-config\src\ini.rs`), which mirrors the same dialect byte-for-byte so the comment-preservation contract is preserved across both readers.
- `resources\stable-diffusion.ico` — installer / shortcut icon. Currently a placeholder (gradient square with "SD" text) generated by a `System.Drawing` one-liner; replace with a proper icon at any time.
- `stable-diffusion-cpp.nsi.template` — NSIS installer template with placeholders (`@VERSION@`, `@STAGING_DIR@`, `@OUTPUT_FILE@`) replaced by `04-package.ps1` into `build\stable-diffusion-cpp.nsi` (transient — deleted after the build). Pages: Welcome → Directory → Components → InstFiles → Finish. **No install-time configuration page**: server.ini / presets.ini / MCP-client configs are all written by the `sd-config` GUI post-install. The Finish page offers a `MUI_FINISHPAGE_RUN` checkbox (default unchecked so silent installs don't pop the GUI) whose handler `LaunchConfigurator` spawns `sd-config.exe` via `Exec '"$WINDIR\explorer.exe" "$INSTDIR\bin\sd-config.exe"'` — the explorer indirection is a standard NSIS trick to drop the installer's admin token so the launched process inherits the calling user's session (otherwise it would write to the admin's `%LOCALAPPDATA%` instead of the user's). `.onInit` only flips `SetRegView 64`. The Start Menu carries two shortcuts: the launcher (`run-server.ps1` via `pwsh.exe`) and "Configure" pointing at `$INSTDIR\bin\sd-config.exe` directly.

## Key conventions

- `common.ps1` is dot-sourced by build/package scripts only (not runtime scripts or `00-install-prerequisites.ps1` / `01-configure.ps1`). Runtime scripts use `$PSScriptRoot` to resolve their own paths.
- The Threads default in `sd-config\src\server_cfg.rs` (`default_threads`) and the runtime fallback in `resources\run-server.ps1` use the **same expression**: `Threads = max(1, floor(cores * 0.5))`. Don't let them drift.
- `build\config-build.psd1` (build-time) uses single-quoted PowerShell-data-file syntax. All other generated config files (`server.ini`, `presets.ini`) are plain INI written as UTF-8 without BOM.
- All build artifacts live under `.\build\` (gitignored): source clone, cmake binary dir, NSIS staging, `config-build.psd1`, generated `.nsi`. A single `rm -rf build\` or `Remove-Item -Recurse -Force build\` returns the repo to a clean state.
- The installer registers in `HKLM\Software\stable-diffusion.cpp` (InstallDir) and supports upgrades (uninstalls previous version first). User runtime state lives under `%LOCALAPPDATA%\stable-diffusion.cpp\`: `config\server.ini` (machine-wide sd-server + ModelsDir — single `[Server]` section), `config\presets.ini` (per-model presets — one `[section]` per model file; hand-edits to non-touched sections are preserved across sd-config rewrites), `logs\sd-server.log` (sd-server stdout/stderr), `logs\mcp-server.log` (MCP bridge log, only when used), `run\sd-server.state` (JSON written by `run-server.ps1` while sd-server is running — pid/host/port/preset, used by `mcp-server.ps1` to detect/manage the live process; removed on graceful shutdown). sd-server itself does not persist generated images to disk; the MCP bridge persists only when the caller explicitly passes a `save_path` to `generate_image`, otherwise it also returns base64 only (matching the built-in web UI). The uninstaller asks (defaulting to No) whether to delete the whole tree, so it survives reinstall/upgrade by default.
- sd.cpp requires `--recursive` git clone because it depends on the ggml submodule. Build output is `build\cmake-build\bin\sd-server.exe` (Windows CMake puts binaries directly in `bin\`); Release / Debug fallback locations are checked when staging.
- Only one GPU backend may be enabled per build (CUDA, Vulkan, or HIP). `01-configure.ps1` auto-probes and picks one with priority CUDA > Vulkan > HIP; `02-build-server.ps1` enforces this.
